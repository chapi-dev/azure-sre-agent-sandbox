# Data boundaries

This module focuses on governance choices that affect where SRE Agent data is processed and how usage is audited.

## Supported SRE Agent regions in this lab

| Region | Azure OpenAI | Anthropic Claude | Guidance |
|---|---|---|---|
| East US 2 | Available | Preferred/default | Good general-purpose US deployment. Choose based on reasoning depth vs. cost. |
| Australia East | Available | Preferred/default | Validate model availability in your subscription before demos. |
| Sweden Central | Preferred/default | Opt-in only | Use Azure OpenAI when EU data residency is required. |

> Anthropic is excluded from EU Data Boundary commitments. For Sweden Central and other EU residency scenarios, prefer Azure OpenAI.

## What data can leave the tenant boundary

The agent can process:

- User prompts and approval text
- Responses generated by the agent or subagents
- Resource metadata collected during investigation
- Log extracts and metric summaries pulled into the conversation
- Audit metadata such as thread IDs, timestamps, and action outcomes

Key points:

- SRE Agent stores conversation history and analysis in the **agent's Azure region**.
- Microsoft doesn't use this data to train models.
- Data is isolated by **tenant** and **subscription** boundaries.
- If you select **Anthropic Claude**, prompts, responses, and resource analysis might be processed in the **United States**.

## Customer-managed keys (CMK)

Treat CMK as a layered control:

1. Use CMK on **downstream services** that support it (for example Key Vault, Storage, Log Analytics/App Insights dependencies, Azure OpenAI or Foundry resources when applicable).
2. Document whether the **SRE Agent resource itself** exposes CMK support in your tenant before making it a compliance requirement.
3. If CMK is mandatory and a dependency does not support it, record that as a governance exception before go-live.

## Network restrictions and private connectivity

SRE Agent still needs public service reachability even in tightly controlled environments.

Required allow-list entries:

- `*.azuresre.ai`
- `sre.azure.com`
- `portal.azure.com`
- `api.applicationinsights.io`

Operational notes:

- Allow both **HTTP** and **WebSocket** traffic; some proxies block chat streaming by default.
- Private endpoints on downstream services are helpful, but they do **not** remove the need to allow the SRE Agent service endpoints.
- If Azure OpenAI, Foundry, Key Vault, or storage uses private networking, ensure the agent's managed identity and trusted-Microsoft-services settings still allow the required calls.

## What AAU consumption should be logged

For governance reviews, capture at least:

- `threadId`
- `subagent name`
- `model provider`
- `prompt tokens`
- `completion tokens`
- `total AAU consumed`
- `timestamp`
- `remediation success / outcome`

This module uses illustrative Log Analytics tables:

- `AgentTelemetry_CL`
- `AgentTokenUsage_CL`

The workbook and weekly cost report aggregate those tables by subagent and provider so you can answer:

- Which subagent is the most expensive?
- Which provider consumes more AAU for the same task?
- Did higher token spend correlate with better remediation success?

## Compliance recommendation

- **EU / regulated workloads:** default to `AzureOpenAI`.
- **US or APAC exploratory workloads:** choose provider per task and document the decision.
- **Operator mode + Anthropic + production:** only allow when hooks, audit logging, and region reviews are already approved.
